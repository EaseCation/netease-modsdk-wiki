# 能力知识协议 v3

上游 Markdown 保持原样。`annotations.json` 关联 API/事件，`concepts.json` 维护共享中文概念，`recipes.json` 维护可复用能力链。构建器生成唯一规范化索引、网页补充及搜索记录；不要在查询脚本中加入接口名、商品名或问法特例。

## 概念

每项有稳定 `id`、中文 `label`、`category`（action/target/property/qualifier）、`aliases`、`parents` 和 `excludes`。别名只写基础概念，不粘贴回归题或完整业务需求。父子关系不能循环。

- `requires_any`：只有上下文也出现指定概念时才启用，适合“等级”等多义词。
- `requires_explicit`：专门能力仅在需求明确提及时优先，如权限控制、第三人称、护甲结算后。
- `context_only`：对象背景不能单独证明能力命中，如“玩家”“界面”。

同义词、上下文与互斥关系在这里维护，使 Wiki 与两个搜索出口同步受益。不要将输入坐标、返回坐标和玩家视角当作同一职责。

## API/事件标注

保留 `id`、`source_sha256`、开发说明和关联来源。`tags` 为最多六个中文基础能力词，不设最低数量；`usage` 用于紧凑开发说明，不重复合同或记录项目过程。

`facts` 的 `status` 为 `unknown` 或 `reviewed`。未知项只有空 `concepts`，不能填充确定事实。已核验项提供：

- `concepts`：真正支持的能力，不能将备注中提及的相关行为都当作本接口能力。
- `operation`、`targets`、`extent`、`phase`、`batch`：已由原文确认的操作、对象、范围、阶段、批量边界；缺少说明时不猜。
- `mutable_fields`：事件允许脚本修改的字段；“发生之前”不等于允许修改。
- 可选 `action`、`subject`、`target`、`property`、`qualifiers`：概念 ID 数组，表达明确的角色与属性。未知角色省略，不能仅从方法前缀推断。
- `evidence`：与正确端侧、组件合同对应的章节路径及哈希；跨接口依赖使用 `source_dependencies`。

`inferred` 保存已有分类线索，仅作软排序提示；不能据此硬排除未知能力。新增及修订的确定性知识写入 facts，并复核证据。普通维护入口不直接修改 inferred。

## 组合关系

每项包含 `id`、`label`、触发概念、端侧、`steps`、`guides`、`cautions` 及步骤来源哈希。步骤引用稳定 API ID。`triggers` 可表达多个触发概念组合；`unverified_concepts` 保留尚未得到证明的限定条件。

组合只描述可复用接入方式，例如捕获与恢复、动画注册与状态驱动。用户的市场案例及具体玩法留在检索题库，不加入通用教程。组合没有完整覆盖限定条件时，必须返回 partial，不能拿注册 API 当作效果已经实现。

## 编译、检索与展示

按端侧标题和 `method in` 边界独立解析，描述、参数、返回和限制不能跨段覆盖。编译会验证协议、身份、概念引用、组合引用、原文哈希及可修改字段；原文未变但解析边界修复时，也须复核受影响的绑定。

检索采用字段独立归一化，别名取最佳匹配；返回值参与召回。概念事实用于核对能力，原文词面匹配用于发现候选。显式冲突单独作为限制证据，未知分类不能静默过滤。结果区分 matched、partial、unknown，候选存在不代表能力完整。

网页默认显示标签，展开后阅读能力、事件阶段、可修改字段、开发说明及限制。同名不同端侧或组件的搜索记录分开生成；各出口保留相同语料指纹。不得用额外标注覆盖错误解析的原始合同。

## 维护与验收

修改知识后运行 `npm run api:build`，再使用配套 Skill 的 `scripts/evaluate.py`、`--market` 与 `--guides` 检查稳定需求、改述、边界和上下文预算。站点运行构建、死链检查与 `npm run docs:algolia -- --dry-run`。这些是文档与真实查询验证，不是游戏实机验收。

v3 不读取旧版知识协议；Wiki 与 Skill 必须配套更新。原始问题、旧成本基线和期望答案的复核差异保留在 Skill 仓库；不得通过删题、填入原题整句别名或扩大预算消除失败。
